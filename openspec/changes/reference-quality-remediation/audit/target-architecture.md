# Target ownership and migration

The existing architecture already puts Codex and filesystem I/O outside the pure core. Keep that boundary. The changes below address different reasons for editing the *same* large file. Start with the two runtime lint modules and the offline evaluation runner. Factory changes can wait for the code-scanning owner and a review of the pinned control-file inventory.

## Runtime traces to preserve

| Consumer | Path through the snapshot | Observable boundary |
|---|---|---|
| Native Codex | Marketplace manifest → plugin manifest → packaged skill → settings reference | Explanations work through instructions. Preference changes invoke an installed CLI. |
| CLI user | Shell wrapper or npm bin → feynman dispatcher → command → Codex config/state adapters | Invalid arguments exit before writes. Install merges owned groups and bootstraps state. Uninstall removes its hook and flag but retains preferences. Reinstall reconciles them. |
| SessionStart | Event validation → state-store reconciliation → pure rules and style selection → stdout | Counter writes are advisory and separate from preferences. A failing backup must preserve the original state. F13 records where a read failure wrongly enters that recovery path. Group and hook trust are separate operations. |
| Bootstrap | Argument parsing → destination ownership/protection checks → copy runtime and delivery files → write ownership marker | Marker is written after copies. Preserve refusal and partial-output handling, especially on retries. |
| Lint | CLI file/stdin → parser/fence classification → rule registry → ordered diagnostics → GCC/JSON reporter | Keep rule IDs, diagnostic locations, mixed-script width, strict exit behavior and stdin vs write-back semantics. |
| Autofix | Frame recognition → eligible content conversion → arrow, junction and separator passes | Preserve unclassified rows, fence policy, transformation order, idempotence and labels. |
| Package | tsc build → stage compiled runtime and delivery files → npm pack → reproducibility comparison → install/smoke | Keep both bin names and compiled imports. Smoke must consume the exact retained tarball. |
| Evaluation / factory | Fixture manifests → isolated runner → evidence files; separately GitHub event → role/controller → policy and receipt checks → decision | Preserve failure evidence and ordering. Offline tests may use fake transports. They cannot approve hosted effects or score a model answer. |

The producer/consumer map for updating imports is [evidence/modules.jsonl](evidence/modules.jsonl); type-only edges are included.

For factory moves, add **every new executable control dependency** to the authenticated inventory for its owner (CONTROL_FILES in scripts/factory-protocol.ts for v1, ROLE_CONTROL_FILES in scripts/factory-roles.ts for the separate role controls), reconcile policy fixtures, test copies and workflow path references in the same commit, and re-run disabled-policy and manifest tests. A move that changes which code is authenticated must stop for review. No hosted activation is needed for the source refactor. For runtime moves update the exact named mutation permissions, architecture tests, compiled import paths, bootstrap and package smoke together. For all moves check scripts, manifests, workflow and doc path literals with a repository search before deleting an import; retain existing public paths. The detailed release and deployment contracts stay in their owning ADRs.

## Smaller owners and test suites

Retain the plain switch in bin/feynman.ts: one visible arm per public command. In cmdBootstrap separate destination checks from copy operations before changing either. buildPackage, verifyPublishedPackage and captureHook have long failure/cleanup paths; keep try/finally at the operation boundary and extract private result checks only. The factory preservation, role authority and role-chain modules each own a single refusal protocol; keep those files and first isolate pure precondition decisions inside preserveOrRemoveBranch, authenticateRoleReservation and validateRoleChain. These are focused exceptions to module splitting, not blanket permissions for long functions.

All test modules are outside the implementation file-length gate. A describe callback spans its registered cases; moving each callback to a new file would hide setup/teardown order. For an oversized individual fixture or helper, group by public behavior (hook, install, receipt, recovery or release) and keep assertions next to the operation. The function register supplies exact ranges for review, including large anonymous handlers. No public CLI, new repository service, runtime dependency or generic adapter layer is needed for these changes.
