# Review standard for Feynman

Apply the existing repository-quality Q01–Q15 and S01–S09 contracts first. Keep the CLI, native skill, hook and maintenance scripts separately reviewable. For example, changing frame notation should affect lint fixtures and the rule implementation. It should not require changing install or the factory. Public package behavior includes output ordering, exit status, hook trust, the state retained by uninstall and preservation of user-authored text.

| Measure | Decision for this repository | Reason and exceptions |
|---|---|---|
| Implementation module | Aim for 250–300 significant lines or fewer. Review above 300. Record physical LOC separately. | A reviewer should be able to trace inputs, the decision and its effects in one sitting. A declarative rule table may stay together if it has one owner and deterministic tests. |
| Executable function | Aim for 20–30 lines or fewer. Inspect at 50 and require disposition above 50. | Keep a short dispatcher with a long exhaustive switch if each arm delegates and argument failures are characterized. A long state machine needs a transition table or evidence that splitting it would obscure ordering. |
| Parameters | Usually three or fewer. Group parameters only when they share a lifecycle or invariant. | An options object passed through five levels with unrelated fields is still five dependencies. Keep public signatures stable during extraction. |
| Nesting and complexity | Review four nested decision levels or a cyclomatic score above ten. PROJECTED review prompts, not rejection gates. | A cursor inside a fence inside a frame already requires three simultaneous conditions. A fourth decision merits a named predicate or an early return. Independent switch arms and fixture registration have different reading costs. |
| Ownership | Parse unknown data once at its I/O boundary. Retain readonly inputs, discriminated results and named local mutation exceptions. | State-store owns preferences and counter reconciliation. Factory authority checks belong in the repository toolchain. A shared file solely for repeated syntax adds a dependency without a shared invariant. |
| Tests | Give each behavior a positive case, refusal/failure case where relevant, and an observable result. | Prefer output bytes, issue locations, child exit status, untouched files and call order to mocks that assert only invocation. Use fixed seeds and report minimized failing cases. |
| Product evals | Assess generated answers under the versioned ASCII protocol. | Unit tests recognize syntax and preserve bytes. Neither metric measures whether a model preserved every source relationship. |

For measurement, report physical lines and a separate significant-line estimate. The inventory estimate removes blank lines, full-line comment prefixes and the shebang. ESLint's token-aware line accounting is authoritative for a future gate; reconcile the estimate before freezing a baseline. Include nested callbacks in the enclosing function's reading span and also count them independently. Do not sum function spans to obtain file size. Test suites and generated lockfiles are outside the implementation size gate. Review complicated test helpers and fixture readability during the owning behavior change.

Use the existing compiler, ESLint and node:test. Only the built-in ESLint file/function line rules were VALIDATED_IN_SANDBOX at their boundaries. The combined gate with exception matching remains PROJECTED. Key each exception by rule, repo-relative path, qualified symbol and digest of the normalized declaration identity (for anonymous callbacks use enclosing declaration plus call-site role and a local distinguishing token). Store its owner, measured size, reason and protecting test. Match exceptions individually, reject new entries or growth without review, and remove stale entries. A rename needs explicit mapping. Do not use line numbers as identity, hash an entire function body, or accept a constant total as proof of no regression.
