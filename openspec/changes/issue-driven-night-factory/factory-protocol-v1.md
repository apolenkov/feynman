## 3. Control release and attempt binding

Activation fixes repository ID, owner ID, controller workflow ID/path, approved control release SHA, a complete transitive control-file/blob manifest (workflow, scripts, policy, tool/runtime/Action pins), schema and fingerprint policy. Mutable workflow name alone cannot authorize anything. Use exact pinned Action commits and checkout control scripts at the approved release SHA with persisted credentials disabled. The workflow bytes executed at its API/context-reported source SHA must equal the approved workflow blob; every executable control input must equal the approved release manifest. Receipt records both the exact execution `workflow_source_sha` and fixed `control_release_sha`. Default ancestry plus unchanged approved control closure permits unrelated default commits; a changed control blob, added executable dependency, unrecognized release or wrong ref requires reviewed policy rotation before any effects. This is fixed control-content/release authority, not blanket approval of descendants. Do not invent a self-referential commit SHA embedded in the very commit it identifies.

For controller workflow_dispatch, require `github.workflow_sha == attempt.head_sha`, `github.workflow_ref` resolves to the fixed path at refs/heads/main, and both match live API bytes. The trusted producer records these values, then the consumer independently compares them. Other adapters use their own fixed workflow tuples, explicitly documented event/source semantics and the same receipt validation; their inputs never certify their own identity. No repair decision relies on branch/model output claiming these fields.

Authority production uses a dedicated job named `factory-authority-<phase>` with a static phase allowlist. It reads validated identifiers/data, constructs canonical receipt JSON, calculates receipt SHA-256, uploads via the pinned immutable action and obtains **actual** `artifact-id` and `artifact-digest` outputs. A final trusted step emits one single-line canonical JSON record after prefix `FACTORY_AUTHORITY_V1 ` containing:

`{schema,kind,run_id,run_attempt,workflow_id,workflow_source_sha,control_release_sha,phase,transition_id,artifact_id,archive_sha256,receipt_sha256}`.

No user/model string is interpolated into shell; the log step emits only validated protocol scalars. The job does not print untrusted bodies or echo its own complete marker source line. Consumer requires exactly one valid marker, successful producer and successful upload/emission steps, and exact job membership in that attempt. The next job can consume proof once producer completes; the whole workflow need not have concluded. Replay of marker text from another job/run fails identity/tuple checks. Artifact creation time must lie within the producing job interval, as an additional check only.

The authenticated job log is the trusted control's declaration of its own actual upload output; the artifact receipt is not its own attestation. This uses the existing trusted-control threat model, not a cryptographic signature or OIDC. A missing, masked, duplicate, unavailable or format-incompatible log marker never falls back to artifact name, receipt.run_attempt, latest run_attempt, timestamps, needs outputs alone or bot author. The proposed producer does not exist yet: actual cross-job availability and rerun isolation remain a required hosted proof, not a capability established by today's unrelated CI sample.

Artifact names: `factory-v1-<kind>-<run_id>-<run_attempt>-<transition_id>`, kind `receipt|checkpoint`. Name collision rejects; `overwrite:true` is forbidden. A rerun cannot manufacture allowance; the production effect gate rejects attempts >1, and a later fresh run can only adopt an already recorded exact operation after reconciliation. A provider reservation is never adopted for reinvocation.

## 4. Canonical state/schema

Version is exactly `factory/v1`; unknown fields/versions are rejected, not silently defaulted. JSON uses RFC 8785 JCS, UTF-8 without BOM/newline, no duplicate keys, no floats/NaN, nonnegative safe integers only for bounded counters, decimal strings for platform IDs and lowercase fixed-length hex for digests/Git object IDs. Explicit nulls are allowed only in explicitly nullable table entries or the phase-specific genesis cases in §5. Those fields remain mandatory; nullable does not mean optional, and absence is not zero. Normalize fingerprints under the separately pinned policy, not generic Unicode normalization. Arrays representing sets sort by canonical byte value and contain no duplicates. Hashes are SHA-256 of canonical bytes. Use a maintained JCS implementation after normal dependency verification, not a custom signature/canonicalization format. [JCS specification](https://www.rfc-editor.org/rfc/rfc8785).

## 5. Bootstrap and legacy import

1. Before activation, reviewed control policy has `activation=disabled`, fixed repository identity and controller control-manifest, and the exact approved bootstrap ticket. Every ordinary admit/reserve/outcome command denies. Runtime cannot infer virgin state from a 404.
2. `bootstrap-ticket.json` is closed `{schema,repository_id,epoch_id,control_release_sha,legacy_mode,legacy_cutoff_sha,legacy_cutoff_at}`. `schema=factory/v1`; `repository_id` is the decimal ID string; `epoch_id` uses the existing policy's validated canonical epoch identifier; release and cutoff are lowercase fixed-length Git IDs; `legacy_mode=quarantine`; cutoff time is a UTC RFC3339 timestamp string. The protected disabled bootstrap policy carries this same explicit ticket after approval. The ticket contains neither its own digest/source Git SHA nor a future activation-policy digest. Only owner-triggered bootstrap under the fixed controller group may consume this reviewed ticket.
3. Snapshot existing canonical issues/PR aliases with complete pagination. Existing identities at/before cutoff are imported `history_status=unknown,repair_state=needs-human` unless reviewed primary run evidence proves exact already consumed reservations, in which case preserve those entries. Missing historical proof never imports zero. Unknown recreated/rebased update identity remains quarantined. Only a provably first post-cutoff canonical identity with complete publisher provenance may start at zero. `legacy-inventory.json` is closed `{schema,repository_id,epoch_id,legacy_cutoff_sha,legacy_cutoff_at,lineages}`; `lineages` is a canonical sorted duplicate-free array of closed `{lineage_id,file_sha256}`. Each ID remains the existing SHA-256(JCS identity) lineage ID; each file digest hashes canonical bytes at `lineages/<lineage_id>.json`. It enumerates exactly all imported legacy lineage files. Existing identity/alias/quarantine/consumed evidence rules remain unchanged. Complete API inventory proof obligations remain; an empty list alone does not prove absence. `legacy_inventory_sha256` is SHA-256 of the canonical inventory file.
4. The authenticated genesis receipt core is the existing closed Receipt core variant selected by `producer_phase=bootstrap` (same existing receipt kind, not a new transition kind). It has every normal core field plus only `bootstrap_ticket,legacy_inventory_sha256`. The ticket equals the canonical root ticket file and protected ticket; the inventory digest equals the canonical inventory file. Normal variants retain their old closed fields without optional bootstrap keys. Genesis has sequence 0, `parent_head:null` and `parent_checkpoint_head:null` as explicit genesis-only exceptions. Existing non-lineage nullable-field rules apply; genesis creates no repair reservation/provider invocation. No receipt embeds its own digest, archive output, or resulting Git head.
5. The bootstrap fields in every checkpoint are closed and mandatory: `schema,repository_id,epoch_id,genesis_head,genesis_receipt_sha256,activation_policy_sha256,legacy_mode,legacy_cutoff_sha,legacy_cutoff_at,bootstrap_completed,phase,legacy_inventory_sha256`. There are exactly two variants, with no absent fields:
   - `phase=genesis`: `genesis_head:null`, `activation_policy_sha256:null`, `bootstrap_completed:false`; `genesis_receipt_sha256` is the already-known SHA-256 of the authenticated canonical receipt core, not null. Repository, epoch, cutoff, mode and inventory digest agree across ticket, receipt and files. No resulting commit SHA or later policy digest appears anywhere in the Git root checkpoint.
   - `phase=active`: `genesis_head` and `activation_policy_sha256` are non-null values for the already-created anchor and digest; `bootstrap_completed:true`. All other shared bindings equal genesis/ticket/inventory. Null or absent anchor fields are invalid. Every subsequent active checkpoint retains the permanent genesis/receipt/epoch/cutoff/inventory and currently reviewed activation-policy digest; reviewed policy rotation/migration rules remain.
6. The Git root payload contains ticket, inventory, imported lineages and the actual authenticated receipt envelope. Its `checkpoint.json` uses the genesis variant above, sequence 0, `previous_external_checkpoint_head:null`, the actual genesis transition ID and receipt digest. `state_payload_sha256` covers all data except `checkpoint.json`, exactly as before. Zero Git parents are allowed only for this one root creation. Canonical hashes are calculated in dependency order; resulting root head G becomes known only after the commit exists. Create the state ref once; never update an existing branch during bootstrap. An existing ref or ambiguous creation outcome requires reconciliation/needs-human, with no update or automatic rebootstrap.
7. After verified root/ref G and successful receipt provenance, upload the external genesis checkpoint. Its existing closed checkpoint core has sequence 0, `state_head:G`, `previous_checkpoint_head:null` (genesis-only exception), actual checkpoint-file/payload/receipt digests and independently authenticated producer tuple. It hashes the real stored root checkpoint file with the genesis nulls, never a fabricated active representation. Existing log/artifact proof and publication interruption rules are unchanged.
8. A separate reviewed active policy then pins G, genesis receipt, epoch, ticket+inventory and approved controller release/manifest, sets `activation=active` and `bootstrap_completed:true`, and removes executable bootstrap. Calculate `P=SHA-256(JCS(actual reviewed active policy bytes))` only after those bytes exist. P is not embedded in the policy whose bytes it hashes or in the earlier root.
9. The first ordinary active transition may read historical `phase=genesis` state only when its head is exactly pinned G, external genesis proof is valid, ticket/inventory/digests match the permanently reviewed anchor, and no intervening or ambiguous bootstrap exists. This is a first-active admission rule, not a generic virgin-state rule. Its append is sequence 1 with parent [G], links `previous_external_checkpoint_head:G` to the verified external genesis, and stores `phase=active` bootstrap with known G/P. External checkpoint sequence 1 binds its actual new head and predecessor G. Sequence >=2 follows normal single-parent/predecessor/active rules.

Any ambiguous prior bootstrap attempt, missing/changed anchor, deleted state branch/artifact, rollback, unavailable provenance or attempted rebootstrap is needs-human, never a new epoch or zero ledger. Human reconciliation may restore exact known history/provenance, not reset an old lineage's two-call allowance. Bootstrap policy/epoch changes require an explicit reviewed migration, outside autonomous behavior. The present 404s support the preactivation finding only; no bootstrap has been performed by this task.

## 6. Append, checkpoint discovery and recovery

Normal sequence:

`independent checkpoint + complete tail -> admission -> receipt upload + completed producer proof -> one-parent state append -> external checkpoint upload + proof -> provider/write gate -> next outcome transition`.

Reservation is consumed at the authenticated reservation receipt even if state append is interrupted; provider requires both durable reservation and external checkpoint verified. Receipt orphan recovery can only record consumed/needs-human; it never invokes a provider under that orphan. Checkpoint creation is mandatory after every accepted transition, including retry claims and conservative orphan accounting. A checkpoint certifies accumulated state, so old receipts before it may expire without forcing replay of all history; its own artifact/log proof and genesis policy anchor must remain available.

Discovery is independent of event-supplied IDs: list repository artifacts and allowed-controller runs with complete pagination, resolve candidate checkpoint producers through attempt jobs/logs and exact release policy, and inspect both completed and noncompleted attempts. Artifact name only narrows candidates after authenticated run identity. For finite availability, each listing is capped at 100 pages of 100 records; reaching the cap without a provably terminal page is needs-human. This is a discovery I/O ceiling, distinct from the 100-record recovery tail. Do not use `created>=checkpoint_time` as the sole run filter: old runs can be rerun and old queued runs can finish later. Inventory discovery must include them.

Among independently verified checkpoint candidates, choose the unique greatest sequence on one state-head ancestry chain. Conflicting same-sequence heads, a higher claimed checkpoint that cannot be authenticated, missing/expired newest known checkpoint, or deletion of a previously referenced checkpoint means needs-human; do not quietly select an older convenient checkpoint. Artifacts from unrelated workflows do not become candidates merely by their names. Then require current state to descend from that checkpoint; walk each parent to head with no merges/gaps, validate changed paths, receipt bytes, exact transition and counters. At most 100 intervening appends AND 100 controller attempts (including cancelled/failed/incomplete attempts); the 101st or incomplete inventory denies. A newer checkpoint is accepted only if its trusted producer followed the same verified predecessor/tail procedure; this is the reviewed control/admin trust root, not validation by self-claimed receipt.

Inspect all post-checkpoint authority receipts, including unappended ones and partial runs; every provable orphan repair reservation is counted consumed before any later repair. If artifact/log association or history is unknown, refuse automatic repair globally until reconciliation rather than risk treating an invisible reservation as zero. Git ancestry alone, artifact expiry and lack of a response cannot restore allowance.

Prepare append from verified head P. Re-read state ref immediately before publication; if it differs, do not transplant the prepared receipt onto a new parent. Commit H must have parent [P] and exact approved tree delta. Publish `force:false`; reread exact H/receipt. Git fast-forward is **not expected-old CAS**: a rolled-back ref could also accept H. Before effect gate, re-prove checkpoint continuity and absence of unauthorized observed changes. The native controller group is the serialization owner, not readback. On a sibling conflict, preserve both objects, refetch complete authoritative state under the same group, reconcile identical transition IDs idempotently, otherwise mark conflict/needs-human. Do not silently reserve twice, force, merge, or claim two local writers atomic because one final ref looks right.

## 7. Retry and interruption decisions

A stage can execute its initial operation once and its same exact operation once more only after a definitive retryable transport failure AND durable `retry_claimed:true` proof made **before** that retry. Persist claimed bits pessimistically; a lost response/unused claim remains spent. Authentication, protection/permission failure, invalid provenance, stale head, unknown classification and provider errors are not retryable transport. Readback GETs may reconcile an ambiguous mutation but may not blindly repeat it. Retry uses identical patch/payload/target/head; it cannot regenerate a patch or call a provider.

Authority bootstrap/upload cannot recursively mint infinite retry receipts. Initial authority upload has no automatic retry if durable retry authorization cannot first be established. Once a verified state exists, a retry-claim transition can authorize one retry of an exact earlier operation; its own receipt/append/checkpoint publication is one-shot and failure is needs-human. A protocol-publication retry therefore exists only when the prior authenticated claim can be recovered. This deliberately sacrifices availability at the first-upload/claim-publication gap; “at most one retry” never promises retry when accounting cannot be made durable. No private store or hidden job retry is introduced. Production disables any outer provider retries; library chunk/network retries must be bounded transport for the same upload/session and cannot imply a second finalized artifact/provider request.

| Interruption / observable outcome | Durable decision and permitted next action |
| --- | --- |
| Before any authenticated reserve receipt exists | No provider. A fully proved no-effect request may be readmitted; unknown upload outcome is not proof of absence. |
| Upload failed definitively before artifact exists, no durable retry claim | Stop needs-human; cannot authorize its own retry from volatile memory. No provider. |
| Upload accepted, action response/emission log missing | Attempt provenance/transport ambiguous; stop, retain possible reservation as unknown-consumed. Discover exact output if later available; never upload a replacement on assumption. |
| Receipt and producer proof complete; append never sent | Authenticated orphan counts consumed; serialized recovery appends conservative reservation+needs-human, then checkpoint. No provider under orphan reservation. |
| Append accepted; response lost | Read exact transition, H and parent/tree/receipt. If identical, retain it; no second reservation. If unknown/conflict, needs-human. |
| Append complete; checkpoint absent/failed | Consumption durable; provider forbidden. Recover <=100 tail from previous valid checkpoint and publish checkpoint once allowed accounting proves operation eligibility; otherwise needs-human. |
| Checkpoint upload accepted, proof/response lost | Discover by authenticated producer/artifact ID; verify exact H. Missing proof stops. Do not replace, refund or blindly reupload. |
| Checkpoint verified; process cancelled before provider | Reservation consumed. Later run cannot invoke provider with that reservation; owner-approved new repair may reserve remaining attempt 2. |
| Provider timeout/cancel/invalid output/unknown response | Consumed once. No provider retry labeled transport. Next repair requires remaining reservation and a fresh authorization. |
| Provider produced patch; accepted exact patch receipt exists | Resume publication of that same digest/head only, within operation allowance. Re-run secretless gates if required; never regenerate a patch as recovery. |
| Remote push succeeds, PR publish fails/response ambiguous | Discover exact branch head and canonical lineage/PR with full pagination, reuse exact commit; bind/create at most one PR with already claimed stage allowance. Unknown/different head preserves work. |
| Retry claim persisted; retry not sent or result lost | Retry remains consumed. Reconcile exact result, never issue a second retry on rerun. |
| Expired/deleted archive or log; unknown source/repo/attempt; foreign state append/rollback | needs-human; keep Git accounting and all known/possible consumption. Neither fallback checkpoint nor bootstrap resets state. |
| Queue overflow or pending cancellation | Delivery failure only; if no reservation exists, no repair was accepted. If reservation evidence exists, preserve it. Dispatch 2xx does not prove admission. |

## 8. Job boundaries and permission compatibility

Artifact upload uses Actions runtime transport, not an extra actions:write scope; consumers use actions:read.
